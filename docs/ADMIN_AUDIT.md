## 2. Competing Implementations & Deduplication Analysis

1. **Authentication:**
   - *Current:* Guardian Bearer token auth in `apps/api/app/auth.py`.
   - *Admin Requirement:* Passwordless magic-link + mandatory TOTP with cookie session.
   - *Decision:* Keep `auth.py` strictly for Guardian API Bearer tokens. Create `admin_auth.py` for `/admin-api` with separate cookie name (`kavach_admin_session`), CSRF tokens, and step-up auth. Do not mix admin and customer sessions.

2. **Waitlist Handling:**
   - *Current:* `apps/site/src/app/api/waitlist/route.ts` proxies to in-memory `mockAdapter.ts`.
   - *Decision:* Re-route `apps/site` waitlist submissions to the real FastAPI endpoint `POST /api/waitlist` with fallback to mock when `NEXT_PUBLIC_MOCK=1`. Deduplicate waitlist schema by sharing field definitions.

3. **Database Migration Strategy:**
   - *Current:* Hardcoded raw SQL in `apps/api/app/db.py:SCHEMA`.
   - *Decision:* Do NOT introduce Alembic, SQLAlchemy, Prisma, or heavy ORM. In accordance with the "Ponytail" principle (YAGNI, minimal code that works), implement a lightweight migration runner (`apps/api/app/migrations.py`) that reads numbered SQL files (`migrations/001_initial.sql`, `002_admin_tables.sql`, etc.), checks `schema_migrations`, runs in transactions, and uses portable ANSI SQL syntax compatible with SQLite and PostgreSQL.

4. **Brand Configuration:**
   - *Current:* String "Kavach" hardcoded in titles, email headers, and constants.
   - *Decision:* Centralize `BRAND_NAME`, `BRAND_DOMAIN`, and `TICKET_PREFIX` in `apps/api/app/config.py`. All API responses, emails, ticket IDs (e.g. `KAV-000123`), and admin UI badges will consume these variables dynamically.
